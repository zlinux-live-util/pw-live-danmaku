# 本机 WebSocket 弹幕源：帧格式 v1

`--ws [PORT]` 在 `127.0.0.1` 上开一个明文 WebSocket，把面板实际画出来的每一行再发一份给本机的
第二个程序：一个 Resonite 文本组件、一个日志、一个机器人，或者一段自己写的脚本。本文只规定
**帧内容**；传输层的行为、限制与安全边界见第 1 节。

本文与 `src/broadcast.{hpp,cpp}` 是同一份契约，改一处必须改另一处。

## 1. 传输与边界

- 一条面板行 = 一个 WebSocket **text 帧**。字段靠帧边界分隔，所以帧内没有换行结束符。
- 只发**合并之后**的行：`--entry-merge` 与 `--gift-merge` 之后是什么，帧里就是什么。同一个人
  连点十次礼物是一个 `count=10` 的帧，不是十个帧。
- 不重放历史。中途连上的客户端只会看到下一条新行。
- 读取慢的客户端积压到 256 条后，新的行会被丢弃而不是无限排队；协议没有重传或序号，客户端可能直接跳到后面的行。
- 服务端到客户端是单向的。客户端发来的数据只会被读掉，只有 `ping` 会得到 `pong`；客户端发 `close` 时服务端回一个 `close`，并回显前两个字节的状态码。
- 只绑 `127.0.0.1`，明文，无 TLS，无鉴权。它是本机管道，**不要暴露到机器之外**。

## 2. 字段编码

每个帧是一个 UTF-8 的 text 帧，字段之间用一个 **Tab**（`U+0009`）分隔。

- 第一个字段永远是**整数类型**，取值见第 3 节。`0` 保留，不属于任何类型。
- 每个类型有**固定的字段数**。空的字段仍然存在：一个空头像会在帧尾留下一个 Tab 和空字符串，
  而不是把那个 Tab 省掉。
- **没有转义机制。** 任一字段里的 Tab、CR、LF、其它 C0 控制字符和 DEL（`0x7F`）都会被替换成
  一个空格（`U+0020`）。这样客户端按 Tab 切分就不可能切错，代价是文本不是逐字节原样：一条
  真的带 Tab 的弹幕，收到时那个 Tab 已经变成了空格。弹幕是给人看的一句话，不是二进制载荷，
  这个交换是故意的。
- 多字节 UTF-8 不会被误伤：续字节都 `>= 0x80`，不落在控制字符范围里。
- 头像 URL 是**每个类型的最后一个已定义字段**。v1 的客户端读到自己的类型需要的字段就够；
  以后新增字段只会追加在它后面，客户端应忽略多出来的尾部字段，而不是因为多一个字段就丢帧。
- 未知类型整帧忽略。类型号和已有字段的位置不会在 v1 内改变。

### 2.1 为什么这样排

- **类型在最前**：客户端读第一个 Tab 之前的内容就能分派，不需要先猜正文。
- **用户名固定在第二**：所有类型取“谁”都是同一个位置，客户端不用为每种类型记一个不同的下标。
- **头像固定在最后**：它是原始数据，不参与富文本；作为已定义字段的末尾，以后加字段只需往后追加。
- **金额用整数分**：浮点数在格式化、比较和跨语言解析时会引入误差；整数分是精确的。
- **数量、人数、时长、船员类型单独成字段**：不把数字塞回 `content`，客户端不需要从展示字符串里反解。
- **空字段保留**：字段数固定，客户端不必为“少一个尾部字段”写另一条分支。

## 3. 类型总表

| 类型 | 名称 | 字段数 | 布局 |
| ---: | --- | ---: | --- |
| 1 | 聊天 `chat` | 4 | `type` `user` `content` `avatar` |
| 2 | 礼物 `gift` | 6 | `type` `user` `verb` `gift` `count` `avatar` |
| 3 | 醒目留言 `super_chat` | 6 | `type` `user` `durationMs` `amountCents` `content` `avatar` |
| 4 | 上舰 `membership` | 5 | `type` `user` `guardLevel` `amountCents` `avatar` |
| 5 | 入场 `entry` | 5 | `type` `user` `count` `content` `avatar` |
| 6 | 点赞 `like` | 4 | `type` `user` `content` `avatar` |
| 7 | 关注 `follow` | 4 | `type` `user` `content` `avatar` |
| 8 | 分享 `share` | 4 | `type` `user` `content` `avatar` |

第二字段永远是发送者/当事用户的显示名（`user`）。这是一个刻意的一致点：客户端先按类型
分派，再取 `fields[1]` 作为“谁”，不需要为每个类型记一个不同的用户位置。

### 3.1 `chat`（类型 1）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `1` |
| 2 | `user` | string | 用户名 |
| 3 | `content` | string | 正文。表情保留发送者输入的 token，例如 `[汤圆]`，因为文本字段显示不了图片 |
| 4 | `avatar` | string | 头像 URL，没有头像框时为空 |

### 3.2 `gift`（类型 2）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `2` |
| 2 | `user` | string | 送礼者 |
| 3 | `verb` | string | 站方给这个礼物的动词，如 `投喂`、`送出`；没有时为空 |
| 4 | `gift` | string | 礼物名，如 `人气票`。**不含数量**，也不含“×N”后缀 |
| 5 | `count` | int | 这一行代表的数量，合并后是总和；最小为 `1` |
| 6 | `avatar` | string | 头像 URL，没有时为空 |

`verb` 与 `gift` 分开，是因为面板给它们两种不同的颜色，客户端也可能只想显示礼物名。要还原
面板上的一行，可以拼成：

```text
{verb} {gift} ×{count}
```

`count == 1` 时是否显示 `×1` 由客户端决定；面板在数量为 1 时不显示。

### 3.3 `super_chat`（类型 3）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `3` |
| 2 | `user` | string | 付费者 |
| 3 | `durationMs` | int | 站方给的停留时长，毫秒；`0` 表示载荷没给 |
| 4 | `amountCents` | int | 金额，人民币**分**；`0` 表示载荷没给 |
| 5 | `content` | string | 付费留言正文 |
| 6 | `avatar` | string | 头像 URL，没有时为空 |

金额用整数“分”而不是 `f32` 元：浮点数表示金额会在格式化、比较和跨语言解析时引入误差，而
“分”是一个精确的整数。`amountCents = 3000` 就是 `CN¥30.00`。目前 B 站的 SC 价格是整数元，
换算不会丢精度。

`durationMs` 来自载荷里的 `time`（秒），乘 1000。面板自己也优先用这个值，只有在载荷没带时长
时才退回到按价格查表。

### 3.4 `membership`（类型 4）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `4` |
| 2 | `user` | string | 上舰者 |
| 3 | `guardLevel` | int | 船员类型：`1` 总督，`2` 提督，`3` 舰长；`0` 表示未知 |
| 4 | `amountCents` | int | 金额，人民币分；`0` 表示载荷没给 |
| 5 | `avatar` | string | 头像 URL，没有时为空 |

`guardLevel` 直接使用站方的编号，不做成字符串：客户端要显示中文名时自己映射，这样协议不
绑定某一版文案。B 站 `GUARD_BUY` 的 `price` 单位是金瓜子，1000 金瓜子 = 1 元，换算后同样以
“分”上线。

### 3.5 `entry`（类型 5）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `5` |
| 2 | `user` | string | 这一批里第一个入场者的名字 |
| 3 | `count` | int | 这一行代表多少人；最小为 `1` |
| 4 | `content` | string | 展示用正文，合并后已经是 `等 N 人进入了直播间` 这样的整句 |
| 5 | `avatar` | string | 头像 URL，通常为空 |

`count` 与 `content` 是同一件事的两种形式：一个给程序，一个给文本组件。客户端选一个用，
不要把 `count` 再拼进 `content`，否则人数会说两遍。

### 3.6 `like`（类型 6）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `6` |
| 2 | `user` | string | 点赞者 |
| 3 | `content` | string | 站方的点赞文案，如 `为主播点赞了` |
| 4 | `avatar` | string | 头像 URL，没有时为空 |

### 3.7 `follow`（类型 7）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `7` |
| 2 | `user` | string | 关注者 |
| 3 | `content` | string | 展示文案，当前是 `关注了主播` |
| 4 | `avatar` | string | 头像 URL，通常为空 |

关注与入场来自同一个 B 站事件 `INTERACT_WORD_V2`，靠 protobuf 的字段 5（`msg_type`）区分：`1`
进入、`2` 关注、`3` 分享。旧版本把所有值都当成入场，所以关注会显示成“进入了直播间”。

### 3.8 `share`（类型 8）

| # | 字段 | 类型 | 含义 |
| ---: | --- | --- | --- |
| 1 | `type` | int | `8` |
| 2 | `user` | string | 分享者 |
| 3 | `content` | string | 展示文案，当前是 `分享了直播间` |
| 4 | `avatar` | string | 头像 URL，通常为空 |

关注与分享不参与 `--entry-merge` 的合并：它们各自一条，不会被折成“等 N 人关注了主播”这样的
汇总行。

## 4. 富文本模式：`--ws-rtf`

`--ws-rtf` **不改变字段的位置和数量**，只改变文本字段的内容：给它们加上
[Resonite 富文本标签](https://wiki.resonite.com/Text_formatting)。数字字段和 `avatar` 永远
保持原样——那些是程序解析的数据，不是给人读的富文本。

被当作富文本的字段：

| 类型 | 富文本字段 |
| --- | --- |
| `chat` | `user`、`content` |
| `gift` | `user`、`verb`、`gift` |
| `super_chat` | `user`、`content` |
| `membership` | `user` |
| `entry` | `user`、`content` |
| `like` | `user`、`content` |
| `follow` | `user`、`content` |
| `share` | `user`、`content` |

具体标记：

- 用户名按面板的优先级上色：发送者自选色优先，否则按角色——普通 `#9AA0A6`，舰长
  `#0F9D58`，房管 `#5E84F1`，主播 `#FFD600`。
- 礼物的动词用礼物金 `#F5C542`，礼物名用礼物粉 `#FB7299`。
- 入场、关注、分享与点赞是环境消息，用户名与正文都套 `<alpha=#80>`，对应面板的 `dimAlpha = 0.5`。
- 观看者自己输入的 `<` 会变成 `<noparse=1><`，一次只保护一个字符。这样做的两个理由：
  闭合形式 `<noparse>...</noparse>` 包不住可能自带 `</noparse>` 的弹幕；而一次一个字符让
  计数单位（字节 / 码点 / UTF-16 码元）变得不重要，因为 `<` 在三种单位下都是 1，弹幕两侧
  却多半是中文，三者互不相同，猜错就会把我们自己的 `</color>` 释放成标记。
- 空字段保持空，不会变成一对空标签。
- 标签语法按 wiki 实现；**在游戏内的实际渲染尚未实测**。

富文本模式下的文本字段是**展示内容**，不是原始数据。需要逐字原文的客户端应该不加
`--ws-rtf`，或把标签当作展示层解析，而不是从中反推用户名和正文。

## 5. 示例

下面的 `\t` 表示一个真实的 Tab，不是反斜杠加 `t`。示例里的头像 URL 用 `<url>` 简写。

### 5.1 纯文本

```text
1\tLoyers\t直接下班吧\t<url>
2\t氧***\t投喂\t人气票\t10\t<url>
3\t五条悟\t60000\t3000\t已经没有什么可怕的了\t<url>
4\txfgryujk\t3\t19800\t
5\tbili_30704624353\t9\t等 9 人进入了直播间\t
6\tstrangeLex\t为主播点赞了\t<url>
7\tl***\t关注了主播\t
8\tl***\t分享了直播间\t
```

逐行对应：

- 普通聊天：`type=1`，用户 `Loyers`，正文 `直接下班吧`。
- 礼物：`type=2`，`投喂` 是动词，`人气票` 是礼物名，`10` 是合并后的数量。
- SC：`type=3`，停留 60000 ms（60 秒），金额 3000 分（CN¥30）。
- 上舰：`type=4`，`guardLevel=3`（舰长），金额 19800 分（CN¥198），没有头像，所以结尾是一个
  空的第 5 字段。
- 入场：`type=5`，这一行代表 9 个人，正文已经包含人数；没有头像，结尾是空的第 5 字段。
- 点赞：`type=6`。
- 关注：`type=7`，正文是 `关注了主播`，没有头像。
- 分享：`type=8`，正文是 `分享了直播间`，没有头像。

### 5.2 `--ws-rtf`

```text
1\t<color=#9AA0A6>Loyers</color>\t直接下班吧\t<url>
2\t<color=#9AA0A6>氧***</color>\t<color=#F5C542>投喂</color>\t<color=#FB7299>人气票</color>\t10\t<url>
3\t<color=#0F9D58>五条悟</color>\t60000\t3000\t已经没有什么可怕的了\t<url>
4\t<color=#0F9D58>xfgryujk</color>\t3\t19800\t
5\t<alpha=#80><color=#9AA0A6>bili_30704624353</color></alpha>\t9\t<alpha=#80>等 9 人进入了直播间</alpha>\t
6\t<alpha=#80><color=#9AA0A6>strangeLex</color></alpha>\t<alpha=#80>为主播点赞了</alpha>\t<url>
7\t<alpha=#80><color=#9AA0A6>l***</color></alpha>\t<alpha=#80>关注了主播</alpha>\t
8\t<alpha=#80><color=#9AA0A6>l***</color></alpha>\t<alpha=#80>分享了直播间</alpha>\t
```

`3` 的名字是绿色，因为 `user_info.guard_level = 3` 让这个用户在这次解析里成为
`UserType::Member`。数字字段 `60000`、`3000`、`19800`、`10` 和头像 URL 都没有被包上标签。

## 6. 客户端检查清单

1. 按 `\t` 切分，不要按空白或按行切分；帧内没有换行结束符。
2. 至少读到第一个字段，按整数类型分派；未知类型忽略整帧。
3. 校验该类型的最小字段数；多出来的尾部字段忽略。
4. 文本字段按 UTF-8 显示；如果开了 `--ws-rtf`，按 Resonite 标签渲染。
5. `amountCents / 100.0` 得到人民币元；不要指望帧里出现浮点数字符串。
6. 礼物显示用 `verb + " " + gift`，数量用 `count` 自己拼；`count` 最小为 1。
7. 入场显示用 `count` 或 `content` 其中之一，不要重复拼人数。
8. 空字符串是合法字段值，尤其 `avatar`。

## 7. 与旧格式的关系

v1 取代了最初的“三个字段：头像 URL、名字、正文”格式。旧格式没有类型，礼物、SC、上舰和普通
弹幕只能靠正文猜；新格式把类型放在第一个字段，把金额、时长、船员类型和礼物数量拆成独立字段。
v1 还把 `INTERACT_WORD_V2` 的进入、关注、分享拆成类型 5/7/8，而不是全部当成入场。
这是一次**不兼容变更**：按旧格式切三个字段的客户端需要改成按类型读取。

`--ws-rtf` 的字段范围也收窄为文本字段：旧格式把名字和正文换成标签，新格式仍然如此，但数字
和头像不再可能被标签污染。
